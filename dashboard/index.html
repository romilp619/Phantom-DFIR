AI Safety Evaluation

AI Safety & Red Teaming

Audit of the adversarial “Skeptic” verification layer in PHANTOM DFIR, and an evidence-grounded replacement.

1. The finding

Claim under test

The tool advertises a Skeptic agent that adversarially cross-examines findings before they can be reported as critical. In the source, that verdict is set by agents/skeptic.py:113-130 from a count of evidence sources, and the audited agent supplies the count.

The count is not independent: agents/evidence.py:83-86 emits one source key per plugin per PID, so a single process observed through four Volatility plugins counts as four separate sources. Separately, correlation/confidence.py:47-48 can clear a fully corroborated threat because the claim text contains the substring "benign".

The verification layer was driven with five different LLM strategies, including no model at all and one that refutes every claim.

All five produced identical confidences on all 300 rows (changed_rows = 0). A verifier that returns the same answer whether it denies everything or agrees with everything is not verifying anything.

The repair fails in 3 families, and that is the honest headline

Failing families, derived from the data rather than asserted: behavioural_mention, identity_alias, network_contact_inflation.

Three of them were not written by us. An independent red-team model was given only the specification of the repair - never the implementation, never the existing attacks - so those attacks test whether the idea generalises instead of probing for code details. All three defeated the repair, each at ASR 1.00, taking the after-score from 0.143 on the fully self-authored set to 0.400. That is the honest number.

The failures are two different kinds, and the difference matters:

Implementation gaps (fixable in principle). identity_alias describes one process under four identity namespaces, so opaque string comparison turns one artifact into four votes - the central rule defeated through its own mechanism. semantic_denial asserts launch count = 0, which is semantically a denial containing none of the negation keywords, so the citation validates. Both are string tests standing in for meanings, the same class of defect as the upstream BENIGN_INDICATORS substring match.

A specification gap (not fixable by code). network_contact_inflation presents four genuinely distinct behavioural artifacts - four ordinary HTTPS connections to the claimed host - and satisfies every rule honestly. The repair confirms while correctly implementing its own specification. The specification equates "mentioned in enough behavioural artifacts" with "established", and contact is not command-and-control.

We deliberately did not patch the two implementation gaps. The identity space is open-ended, so PID extraction still leaves GUID and path namespaces distinct and the alias attack survives a partial fix; and any lexical negation test is evaded by the next construction that means "no" without writing it. Patching would fit the numbers to this particular red-teamer rather than produce a more correct verifier. The stronger conclusion: the repair's central rule is not deterministically enforceable, because "the same artifact" and "denies the claim" are both open-ended judgements - which is exactly what the fine-tuned model was meant to supply, and why the blocked model half is where the remaining failures live.

The same gap, found independently by us first

behavioural_mention was written by us after the verifier was frozen. Four genuine behavioural artifacts each merely name the file while describing ordinary activity: no executable regions, a loopback-only listener, only system DLLs loaded.

The repair confirms all 50 of these rows, at ASR 1.00 both before and after. Notably, the independent model found the same class of hole from the specification alone - convergent evidence that this is a structural gap rather than one we happened to guess.

The lesson: behavioural relevance is not evidential weight. The first two versions of the repair shared this flaw at different depths: v1 treated a scan log as corroboration, v2 treated four innocuous behaviour records as corroboration. Both count name mentions, and so does the upstream defect.

4. Two silent defects in our own harness

The held-out run first disagreed with the tuned run, which was impossible if both measured the same verifier. They were not.

1. The plugin field was dropped. Rebuilt rows defaulted to "unknown", so no artifact could ever be behavioural. It reported capability retention of 0.660 on untouched control rows.

2. Artifact identity collapsed into the evidence id. Five evidence items describing one PID looked like five distinct artifacts, defeating the exact rule the repair is built on, and reported count_inflation ASR 1.00.

Neither raised an exception. Both produced a results table. The fix is structural: the evidence fence now carries id, artifact and plugin; a missing field is a hard error rather than a default; one parser is shared by the dataset builder and the evaluator; and a round-trip gate re-runs the verifier on every rebuilt row at build time - 2,800 rows - asserting that verdict, artifact count and citations all reproduce.

Measured at two thresholds because the scanner's contract deliberately keeps some families below the decisive bar: analyst_addressing and evidence_dismissal are MEDIUM by design, so a HIGH-only measure understates coverage. Both are reported so neither is mistaken for the other.

Detection gaps: conclusion benign, conclusion malicious. These payloads match no scanner rule at any severity. The direct-instruction families are caught; the ones that frame a conclusion or dismiss evidence in realistic prose are not.

No false positives. 0 of 10 hostile-but-benign forensic samples were reported as manipulation attempts. IRC botnet channels, mimikatz paths, reverse-shell strings and persistence registry keys all appear routinely in real evidence; a scanner that flags them gets switched off within a week. Distinguishing text that looks nasty from text that manipulates the analyst is the requirement, and it holds.

Evidence integrity preserved. 0 of 10 artifacts were modified by scanning. Original evidence is hashed and left byte-identical, so findings stay separated from the material they describe.

6. Data curation pipeline

The brief requires the sponsor's toolkit chained into a real pipeline, not described. CuratorKIT 0.1.26 was run over the full training split, and it surfaced three defects that fail silently.

Exact deduplication removed 1,400 rows (42.4%), which is a property of the generators rather than a defect: each family reuses one evidence block across many rows while varying the framing. The effective corpus is 1,900 distinct texts, and that is the number this project reports.

1. An unrecognised format string silently drops the whole corpus. Passing format="jsonl" does not raise. It falls back to UNKNOWN and rejects 100% of rows, with RejectedSample carrying no reason, so the run reports an empty stage table and nothing to act on.

2. Default cleaning deletes the evidence markers. TextCleaner.strip_html removes tag-shaped text. Here the angle-bracket markers are the evidence anchors, so the default removed every one while the run reported a clean pass rate of 1.000. Measured on the same input: 0 of 1,900 rows kept their markers by default, 1,900 of 1,900 with the fix.

3. A non-zero injection rate is a silent no-op without injection types. injection_rate=0.10 produced identical counts to 0.0, no injected rows, and an empty diagnostics dict.

A pipeline that reports success while destroying its own training signal is the worst failure mode there is, and it is the same defect class this project audits elsewhere.

Hardened runner. All three are now refused before the run and verified after it, in phantom_ai_safety/curation/guards.py: the format is validated against the toolkit's own enum; strip_html is disabled for this corpus; a rate without types is rejected with an explanation; and a post-run check fails loudly if every row was rejected or if markers vanished. The run above passed both guards.

  • strip_html disabled so angle-bracket evidence markers survive cleaning
  • format validated against DataFormat; 'jsonl' would reject 100% of rows silently
  • a non-zero injection_rate without injection_types is refused

7. What this does not claim

no fine-tuned model no real memory image no Volatility no upstream benchmark reproduced synthetic evidence only

Every number here comes from the deterministic verifier evaluated on synthetic evidence with the tool layer stubbed. No training run has been performed: all 13 candidate Cohere checkpoints are gated and return HTTP 401 without an authenticated token.

The disjoint-seed replication reproduces these figures exactly, which rules out seed luck and per-row memorisation. It does not rule out generator overfitting, because both splits come from the same eight generators - which is precisely why the one genuinely unanticipated attack, family 8, matters.
